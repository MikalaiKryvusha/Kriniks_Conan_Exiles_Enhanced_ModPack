# Дождь в Conan Exiles Enhanced — как он устроен

> **Создан:** 2026-09-09 · **Родитель:** заказ владельца «дождь виден на больших отдалениях,
> появляется из воздуха; нужно сильно повысить высоту дождя» ·
> **Статус:** устройство найдено офлайн, живые числа СНЯТЫ 2026-09-09 20:03 · причина заказа названа ·
> **Вовне:** решение о правке — слово владельца

## Заказ

Дословно: *«дождь из воздуха появляется на больших отдалениях камеры — видно; нужно сильно
повысить высоту дождя»*.

## Чем это НЕ лечится (проверено, чтобы не искали заново)

- **Настройками.** В конспекте `dw.*` (264 переменные слоя Dreamworld, все девять семей) есть
  только выключатель погоды — высоты нет.
- **Cvar-ами.** Скан 4416 переменных из бинарника игры: про дождь нет ничего.

## Как устроено на самом деле

Найдено **без запуска игры**, за две минуты, индексом IoStore
(`KUMM/researches/ue5-iostore-index/utoc-index.py`, 138 424 пути из 37 контейнеров):

```
python researches/ue5-iostore-index/utoc-index.py "<игра>/Content/Paks/"*.utoc > assets.txt
grep -i "Systems/Weather" assets.txt
```

```
Systems/Weather/BP_AC_Weather                     компонент погоды
Systems/Weather/BP_SC_WeatherHandler              управляющий
Systems/Weather/WeatherClimates                   климаты
Systems/Weather/WeatherConditionsTable            таблица условий
Systems/Weather/WeatherSystems/
    BP_DynamicWeather_Master                      общий мастер
    BP_DynamicWeather_Rain                        САМ ДОЖДЬ
    BP_DynamicWeather_Thunderstorm
    BP_DynamicWeather_Sandstorm · _Snow · _Ash
    BP_ConstantHeavyRain
    BP_Dynamic_Weather_ExiledLands_Highland_Rain  дождь Земель Изгнанников
    BP_Dynamic_Weather_Siptah_Rain
    Weather_SceneCapture2d_Rain                   ← ГЛАВНОЕ
    Weather_RenderTarget_Rain
    Weather_RenderTarget_Rain_Processed
    M_DepthCapturePostProcess
```

**`Weather_SceneCapture2d_Rain` — вот объяснение жалобы.** Игра ставит над игроком камеру,
снимает мир сверху вниз в текстуру `Weather_RenderTarget_Rain`, обрабатывает её
(`_Processed`) и по ней решает, куда каплям падать, а куда нет — так дождь не идёт под крышей
и под деревьями. У любой такой съёмки есть **высота над игроком** и **охват по горизонтали**.

Отсюда прямое следствие: **за пределами охвата маска не определена**, и капли начинаются там,
где начинается объём съёмки. Игрок с отведённой камерой видит эту границу — и описывает её
ровно теми словами, что и владелец: «появляется из воздуха».

## Как это снимается

Зонд — **Numpad 1** в моде камеры. Класс `SceneCaptureComponent2D` добавлен в его список
09.09.2026 вместе с подсказкой `scenecapture`; без этого он не увидел бы главного объекта.

✅ **Дождя ждать НЕ надо** — вопреки тому, что мы думали полдня. Съёмка живёт в мире
постоянно: это часть системы погоды, а не эффекта. Числа сняты при ясном небе.

⚠️ Раньше зонд молчал по двум причинам сразу: искал не те классы и показывал только первые
12 строк из 31, которые целиком забивала песчаная буря из вступительного ролика (тридцать
её экземпляров висят в памяти всю сессию). Оба дефекта устранены.

## Ловушки этого разбора

1. **Слово `storm` есть в `sandstorm`.** Любой поиск по «storm» первым делом приносит песчаную
   бурю. Отсюда фильтр `RAIN_SKIP` в зонде.
2. **Прибор, который НАШЁЛ, но не ПОКАЗАЛ, выглядит как ответ.** Строка «похожих на погоду 31»
   при двенадцати показанных читалась как «дождя нет». Теперь зонд печатает и сколько скрыл,
   и почему.
3. **Ждать погоду дороже, чем прочитать диск.** Час ожидания дождя в живой игре не дал бы и
   половины того, что дал индекс IoStore за две минуты. Правило общее: у игры на UE5 устройство
   ЛЮБОЙ системы читается с диска без запуска.

## ЧИСЛА СНЯТЫ В ЖИВОЙ ИГРЕ — 2026-09-09 20:03 +03:00

Зонд (Numpad 1) прочитал единственный экземпляр
`Weather_SceneCapture2d_Rain_C.NewSceneCaptureComponent2D`. **Дождь для этого ждать не
понадобилось: съёмка живёт в мире постоянно, она часть системы, а не эффекта.**

```
OrthoWidth              = 4096.0
ProjectionType          = 1          орто (вид сверху без перспективы)
CaptureSource           = 4
FOVAngle                = 1.7        для орто не используется
MaxViewDistanceOverride = 30000.0
bCaptureEveryFrame      = false
bCaptureOnMovement      = false
RelativeLocation        = X=0 Y=0 Z=0    (крепится к владельцу)
мировое положение       = X=1287627.5 Y=-23581.7 Z=-14491.1
```

### Ответ на заказ, в одном числе

**`OrthoWidth = 4096` — это 41 метр** (в Unreal единица = сантиметр). Квадрат 41 × 41 м вокруг
игрока — вся область, где игра знает, куда дождю падать. За его краем маска не определена.

Владелец отводит камеру и видит на экране пространство в сотни метров, а дождь нарисован
только в этом квадрате. **Край квадрата и есть «дождь появляется из воздуха».**

Жалоба была про ВЫСОТУ, а число оказалось про ОХВАТ — и это тот случай, когда наблюдение
поправило формулировку заказа.

### Что с этим можно сделать — и чего это стоит

Поднять `OrthoWidth`. ⚠️ **Цена известна заранее и её надо назвать до правки:** текстура
(`Weather_RenderTarget_Rain`) остаётся прежнего размера, поэтому вдвое больший охват — вдвое
грубее маска на метр. Признак перебора: дождь начнёт «протекать» под навесы и кроны, потому
что маска перестанет их разрешать.

Порядок работы, по одному шагу за запуск:
1. Снять разрешение `Weather_RenderTarget_Rain` — без него о цене можно только гадать.
2. Пробовать `OrthoWidth` шагами ×1.5 (4096 → 6144 → 9216), каждый раз проверяя под навесом.
3. Мерить кадры прибором `perf-harness`: съёмка сцены — это отдельный проход рендера.

**Ничего из этого ещё не пробовано.** Правка меняет ЧУЖОЙ объект игры каждый кадр, а такие
правки у нас делаются только по слову владельца.

## 🔴 ТЕОРИЯ ОХВАТА СЪЁМКИ ОПРОВЕРГНУТА — 2026-09-09 22:00

**`OrthoWidth` съёмки дождя НЕ управляет дальностью дождя.** Проверено владельцем в живой игре:
клавишей Numpad `.` значение переключалось между 4096 и 12288 **двенадцать раз**, каждое
переключение подтверждено чтением обратно в журнале —

```
переключатель охвата: 12288.0 -> 4096.0 (41 м)
переключатель охвата: 4096.0 -> 12288.0 (123 м)
```

— и картинка **не изменилась ни разу**. Слова владельца: «нум точка ничего не меняет, дождь как
был из неба и вблизи, так и остался».

Запись проходит, эффекта нет. Значит съёмка нужна для другого — почти наверняка для маски
окклюзии (чтобы не капало под крышей) и накопления мокрости, что и следует из её пары
`Weather_RenderTarget_Rain` / `_Processed` и материала `MF_FLXRainOcclusion`.

**Как была допущена ошибка, чтобы не повторить.** Я нашёл съёмку, увидел, что она снимает мир
сверху, и ДОСТРОИЛ в голове, будто её охват задаёт область дождя. Объяснение звучало убедительно
и сходилось с жалобой — и было выдумкой. Правило нарушено прямо: пробел закрывают источником или
проверкой, а не правдоподобным рассуждением (`PHILOSOPHY.md` → три двери).
Правка откачена, `rain_ortho_width = 0` (не трогать).

## ✅ НАСТОЯЩАЯ ЦЕЛЬ — система частиц, а не съёмка

Найдено тем же индексом IoStore:

```
FLX/VFX/Particles/Weather/NS_EXL_Precipitation           ← дождь и снег
FLX/VFX/Particles/Weather/NS_Localised_Precipitation      ← локальные осадки
FLX/VFX/Particles/Weather/NS_EXL_Ashlands_Precipitation
FLX/VFX/Materials/Weather/M_EXL_RainSheet                 ← «полотно» дождя
FLX/VFX/MaterialInstances/Weather/MI_EXL_RainSheet_NoOcclusion
```

**Механизм — из документации Unreal и практики Niagara, а не из головы.** Дождь спавнится в
КОРОБКЕ, привязанной к игроку, и у эмиттера стоят ФИКСИРОВАННЫЕ границы: пересчитывать границы
каждый тик при тысячах частиц слишком дорого. Дальность дождя определяют две величины:

1. **размер коробки спавна** — где вообще рождаются капли;
2. **фиксированные границы системы** — за ними Niagara просто перестаёт рисовать.

Край коробки и есть та граница, которую владелец видит как «дождь появляется из воздуха».
